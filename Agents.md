# Python Agent Instructions

These repository instructions apply to all Python implementation and maintenance work. The architecture reference is [architecture.drawio](architecture.drawio); the phased checklist is [Plan.md](Plan.md).

## Product requirements

- Build a local-only D&D adventure application with a basic Streamlit UI. Authentication is out of scope.
- Replace the basic LLM chat loop with LangChain-integrated tools and LangGraph agent flows. Support both ReAct and Plan-Execute-Revise; persist the selected workflow per adventure.
- The language model is hosted locally and is responsible for generating the adventure. Never commit model weights or machine-specific model paths.
- Players supply the world details and starting characters and may supply adventure pointers. The UI must accept this information through text and/or file upload. Do not silently invent player-owned world, character, or campaign facts.
- Support multiple D&D editions through edition-specific Chroma collections. Load an edition's collections lazily and always filter retrieval by the active edition. Do not blend editions.
- Support semantic memory, structured local/current-adventure memory, and episodic memory. Scope chat data by stable user and adventure identifiers; preserve provenance and timestamps.
- Players must be able to save, pause, list, and resume an adventure with its edition, workflow, player inputs, graph checkpoint, chat, and campaign state.
- Include at minimum a monster generation tool and a dice tool supporting d4, d6, d8, d10, d12, d20, and d100. Dice outcomes must be generated by the tool.
- Keep shared defaults and registries, especially supported dice and edition/collection metadata, in root `config.py` as the single source of truth. Avoid duplicate registries and hard-coded local paths elsewhere.

## Python implementation practices

- Use type hints, small cohesive modules, explicit data models for graph state and tool inputs/outputs, and clear error messages.
- Keep secrets and machine-local settings in environment/local configuration. Keep model files, Chroma persistence, user saves, and checkpoints outside git.
- Treat player-provided campaign material as authoritative input; clearly distinguish sourced rules from generated story and generated monsters.
- Keep graph loops and tool retries bounded. Validate tool inputs before side effects, and keep adventure state updates structured and recoverable.
- Make Streamlit reruns safe; durable adventure/checkpoint storage must not depend only on `st.session_state`.
- Preserve edition and adventure scoping in retrieval and memory operations.
- Update [Plan.md](Plan.md), [README.md](README.md), and [architecture.drawio](architecture.drawio) when implementation decisions materially change.
- Do not claim the planned app is implemented until it is. The current `Python/` folder is a legacy console/FAISS prototype.

## Work sequencing

Follow the phase order in [Plan.md](Plan.md). Mark checklist items complete only after their deliverables have been implemented and reviewed. Phase 1 foundation and configuration are implemented; do not claim later phases are complete until their deliverables are reviewed.
